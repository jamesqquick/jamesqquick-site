# Map the Application Architecture

## Outcome

By the end of this lesson, you will know where each kind of Weekender code lives and how data moves from Markdown files to generated pages. This map will keep later implementation decisions grounded in the finished project.

## Read the top-level project

The finished application keeps application code under `src/`, static files under `public/`, and tests under `tests/`. This is the target structure you will build during the course.

```text
weekender/
|-- public/
|-- src/
|-- tests/
|-- astro.config.mjs
|-- package.json
|-- playwright.config.ts
|-- tsconfig.json
|-- vitest.config.ts
`-- pnpm-lock.yaml
```

`astro.config.mjs` selects static output, registers React and sitemap integrations, and adds Tailwind CSS 4 through its Vite plugin. `tsconfig.json` extends Astro's strict preset and configures React's JSX transform. `package.json` contains development, build, formatting, linting, type-checking, unit-test, and browser-test commands.

The project does not have a custom server entry point. Astro can generate the public site into `dist/` because the route set and source content are known during the build.

## Map the source folders

The `src/` directory is organized by responsibility:

```text
src/
|-- assets/events/       Local event poster artwork
|-- components/          Astro components and React islands
|-- content/events/      Event Markdown entries
|-- content/venues/      Venue Markdown entries
|-- layouts/             Shared document shell
|-- lib/                 Content and browser-state logic
|-- pages/               File-based routes
|-- styles/              Tailwind theme and global rules
`-- content.config.ts    Collection schemas
```

This is intentionally shallow. Each folder answers a direct question. Pages define URLs. Layouts define the shared document. Components render reusable interface pieces. Content stores editor-owned records. Library files hold logic that does not belong to one page.

## Trace one event to the browser

Start with `src/content/events/riverfront-sunset-sessions.md`. Its frontmatter stores structured values such as title, start time, venue reference, category, price, image, alt text, accessibility notes, and featured status. Its Markdown body stores longer editorial copy.

`src/content.config.ts` defines the `events` and `venues` collections. Astro validates every entry against these schemas. The event schema also declares `venue` as a reference to the venue collection, so the relationship is checked instead of remaining an arbitrary string.

`src/lib/content.ts` is the data access boundary. `getPublishedEvents()` loads non-draft events and sorts them by start time. `getEventsWithVenues()` resolves each event's venue and returns pairs with this shape:

```ts
export interface EventWithVenue {
  event: CollectionEntry<"events">;
  venue: CollectionEntry<"venues">;
}
```

Pages and components consume that result instead of repeating collection lookups. If a referenced venue cannot be found, the helper throws `MissingVenueError` with the event ID. Failing during the build is better than shipping an incomplete card or broken venue link.

`src/pages/index.astro` queries those event and venue pairs. It selects featured events, computes category counts, and renders the editorial home page. `src/components/events/EventCard.astro` receives typed event and venue entries and handles the repeated card markup.

The final result is HTML generated by Astro. No React runtime is required for the home page's event cards.

## Separate static UI from browser state

Most components use `.astro` because they render content and links without browser state:

- `BaseLayout.astro`
- `SiteHeader.astro`
- `SiteFooter.astro`
- `EventCard.astro`

Four components use `.tsx` because they need state, effects, or browser APIs:

- `EventExplorer.tsx`
- `SaveEventButton.tsx`
- `SavedCount.tsx`
- `SavedPlan.tsx`

The extension is not the only distinction. A React component becomes interactive in the browser only when an Astro template gives it a client directive. The finished application uses `client:load` for all four because their state should be available as soon as the page loads.

Data crosses the Astro-to-React boundary as serializable props. For example, `src/pages/events/index.astro` loads full content entries on the build side, converts them to `EventSummary` objects, and passes the summaries to `EventExplorer`. React receives strings, numbers, and arrays rather than Astro collection objects with `Date` values and image metadata.

## Map routes to files

Astro's file-based router makes route ownership visible:

| Source file                             | Public route              |
| --------------------------------------- | ------------------------- |
| `src/pages/index.astro`                 | `/`                       |
| `src/pages/events/index.astro`          | `/events/`                |
| `src/pages/events/[id].astro`           | `/events/[id]/`           |
| `src/pages/categories/[category].astro` | `/categories/[category]/` |
| `src/pages/venues/[id].astro`           | `/venues/[id]/`           |
| `src/pages/saved.astro`                 | `/saved/`                 |
| `src/pages/about.astro`                 | `/about/`                 |
| `src/pages/404.astro`                   | `/404.html`               |
| `src/pages/rss.xml.ts`                  | `/rss.xml`                |

Bracketed filenames are dynamic route templates. Because the project uses static output, each dynamic page exports `getStaticPaths()` so Astro knows which concrete paths to build.

## Understand the test boundary

The tests mirror the architecture. `tests/unit/` checks pure filtering and saved-event logic as well as React components. `tests/e2e/` checks route integrity, user journeys, mobile layouts, and accessibility in Chromium. `tests/setup/vitest.ts` prepares the component-test environment.

Pure logic in `src/lib/` is fast to test without a browser. Playwright is reserved for behavior that depends on navigation, layout, local storage, or the accessibility tree.
